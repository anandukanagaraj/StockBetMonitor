# StockMonitor V3: code and functional review (26 Nov 2026)

Scope: auth and multi-user isolation, stock and options P&L, scheduler alerts,
fund NAV and investor units, simulations, the published report, data safety.
Every finding below was checked against the code, and where possible against
the live data and logs on this laptop. Nothing was changed.

**Status (26 Nov):** P1 items 1, 2, 3 and 5 are fixed and covered by
`tests/test_p1_fixes.py`. Item 4 (public report contents): kept as is by
decision; the full track record, including position sizes, is meant to be public.

**Status (26 Nov, P2):** items 6-10, 12-16 and 18-21 are fixed and covered by
`tests/test_p2_fixes.py`. Item 21: `.venv` is now built from the system Python
3.13 (old environment kept as `.venv-codex-old`). Two items are open because
they are product decisions rather than bugs:
- **Item 11 (multi-user alerts):** the scheduler still monitors only the admin's
  `STOCK_GROUP_CODES` groups and sends to one recipient.
- **Item 17 (net-of-charges P&L):** charge rates are now configurable (item 18),
  but P&L figures are still gross.

**Status (26 Nov, P3):** items 22-28 are fixed.
- 22: `services/schema.py` runs all migrations once, under a cross-process lock,
  and records `SCHEMA_VERSION` in `app_schema_version`.
- 23: one copy each of `realized_pl` (`services/pl_core.py`) and option max-risk
  (`services/option_charges.py`; checked identical on 5,000 random strategies).
- 24: `app.py` 3,457 → about 2,500 lines; P&L, options analytics and config
  settings moved to `services/pl_core.py`, `services/options_analytics.py`
  and `services/app_config.py`. Routes and URLs unchanged.
- 25: `tests/test_web_layer.py` renders every page with data and checks login,
  CSRF, admin-only pages and user isolation.
- 26-28: logging controlled by `LOG_LEVEL` (default INFO, no per-request lines);
  Telegram reminder when holidays for this year (or next, in December) are
  missing; `/health` no longer shows file paths.

The new web-layer tests found two bugs that this review had missed, both fixed:
- **Any logged-in user could delete another user's option strategy** by ID
  (`/options/<id>/delete` did not use the owner-filtered lookup). This
  corrects "What looked solid" below.
- **The option strategy detail page crashed** for every strategy (raw database
  rows passed to code expecting dictionaries). It went unnoticed because the live
  database has no option strategies.

Priority: **P1** fix soon (money, data loss, security or daily annoyance),
**P2** worth fixing, **P3** structural, makes future changes safer.

## P1: fix soon

### 1. The same alert is re-sent every 30 minutes, each one also by email
`scheduler.py` `run_market_check` → `send_alert`. There is no record of what was
already sent, so every market check re-sends TARGET HIT / NEAR TARGET /
VERY CLOSE / STOP LOSS for the same bets. `send_alert` also sends an email for
every alert, not only when Telegram fails.

Evidence from `logs/`: 23 Nov had 58 alerts over 12 checks; RELIANCE, ITC,
INDIGO and ULTRACEMCO were each alerted 11 times that day.

Fix: store the last status sent per position, and alert only when the status
changes (e.g. HOLD → NEAR TARGET → TARGET HIT), plus at most one reminder a day.
Send email only as a real fallback, or as one daily digest.

### 2. Database backups stopped in August, and the backup script misses recent changes
- The newest file in `data/backups/` is from **11 Aug 2026**. Nothing runs
  `backup_db.ps1` automatically. The database (all bets, funds and investor
  records) exists only on this laptop.
- `backup_db.ps1` uses `Copy-Item` on `stock_monitor.db`. The database runs in
  WAL mode, and right now 4 MB of recent changes sit in `stock_monitor.db-wal`,
  so a plain file copy can leave out recent edits.
- Its "keep 30" clean-up pattern `stock_monitor_*.db` also deletes the
  `stock_monitor_before_*` milestone backups.

Fix: back up with SQLite's backup API (`sqlite3 ... .backup` or Python
`connection.backup()`), run it daily from the scheduler after EOD, and copy the
result off the laptop (OneDrive/Google Drive folder is enough).

### 3. The bootstrap admin password keeps working after you change it
`app.py` `login()`: `valid_bootstrap_admin` checks the password against
`ADMIN_PASSWORD_HASH`, or the built-in default `admin123` when that isn't set,
**on every login**, not just the first. On the laptop no hash is set, so
`admin` / `admin123` logs in even after the password was changed in the UI.
It also skips the `is_active` check. `change_password` accepts the same
bootstrap password as "current password".

Fix: use the bootstrap password only when the admin user has no password hash
yet. After that, check only the hash stored in the database.

### 4. The public GitHub Pages report shows your full holdings
The "masked" report published to the public `public/` repo hides only the
target price. The embedded data still includes, for every bet: ticker, quantity,
buy date, buy price, invested amount, sell date and sell price (200 entries in
today's report).

If that is intended, ignore this. If "masked" was meant to hide position size,
drop `qty`, `buyPrice` and `investedAmount`/`invested` from the masked
version and show percentages only.

### 5. Back-dated fund subscriptions get today's NAV
`fund_management.py` `add_investor`: units are always `amount / today's NAV`,
but the form accepts any `transaction_date`. A subscription entered today for
money received last week is priced at today's NAV, which over- or under-issues
units and shifts value between investors.

Fix: price units at the NAV for the transaction date (from
`fund_nav_snapshots`), or don't allow back-dating.

## P2: worth fixing

### Funds and NAV
6. **Fund cash depends on when a bet was typed in, not when it was bought.**
   `_automatic_stock_cash_flows` compares each position's `created_at` (database
   insert time) with the fund's start. Deleting and re-adding a bet, or
   re-importing from Excel, counts it as a brand-new purchase and moves fund cash
   and NAV. Use `buy_date` / `sell_date`.
7. **NAV history is recorded only when someone opens the fund page.** The value
   saved for a day is whatever it was at that moment, not the closing NAV, and
   days with no visit are missing. Investor returns are based on this history.
   Record the NAV from the scheduler after EOD instead.
8. **Market value silently uses the buy price when there is no current price**
   (`_stock_assets`). Flag these on the page so NAV isn't quietly stale.

### Alerts and monitoring
9. **A failed price fetch quietly removes that bet from alerting.** In
   `refresh_open_position_prices`, failed tickers go to `failed_rows` and are
   never evaluated, so a stop loss can be missed with only a log warning.
   Send one alert listing tickers with no price.
10. **The `ENABLE_STOPLOSS` setting in `config.ini` does nothing.** No code reads it.
11. **Other users' bets are never monitored.** The scheduler runs as the admin
    user and watches only groups listed in `STOCK_GROUP_CODES` (`SWING`). Users
    created in the UI get their own groups (`SWG<id>`), and every alert goes to
    the single recipient in `config.ini`, even though users have Telegram and
    WhatsApp fields. Either support per-user alerts or say clearly that the
    app is single-user.

### Security
12. **Open redirect after login:** `redirect(request.args.get("next"))` accepts
    any URL, so a link like `/login?next=https://evil.example` sends a user off-site
    after a real login. Allow only paths starting with `/`.
13. **Disabled users stay logged in.** `login_required` checks only the session,
    and `is_admin` is cached in it. Re-check the user's `is_active` (and admin flag)
    on each request.
14. **No limit on login attempts.** Add a short lockout after repeated failures
    once the app is reachable beyond the laptop.
15. **The API returns every user's data combined.** `/api/portfolio/actual-pl` has no
    user context, so the owner filter is skipped. Fine while single-user; scope
    it to a user if more users are added.
16. **API key check is skipped for requests that look local** when
    `PORTFOLIO_API_KEY` is unset. Behind a same-host reverse proxy without
    `TRUST_PROXY`, every request looks local. Require the key whenever the app
    isn't bound to localhost.

### P&L and charges
17. **All realized P&L is gross.** Stock P&L is `(sell - buy) × qty`, and option P&L
    is the sum of leg differences. Brokerage, STT, exchange charges, stamp duty, DP
    charges and tax are only applied in the options what-if report, even though
    the rates exist in `services/option_charges.py` and the tax rates are in
    `config.ini`. Dashboard, P&L calendar, API, fund NAV and year-wise totals
    all overstate profit. A "net of charges" figure next to gross would make the
    numbers match the broker's statement.
18. **Charge rates are hard-coded** (`OPTION_STT_RATE = 0.0015`, exchange, stamp
    and DP rates, ₹20 per order). They change with budgets and broker plans. Move
    them to `config.ini` with an effective date, and check them against the current
    NSE circular and your broker's charge sheet.

### Data and performance
19. **The simulation cache grows forever.** `stock_profit_booking_simulation_cache.json`
    is 54 MB with 9,555 entries. The cache key includes today's date, so all
    ~125 tickers are stored again every day (86 days so far), and nothing is pruned.
    The whole file is rewritten on each run, from both the web app and the
    scheduler, without an atomic write, so a crash or overlap can corrupt it
    (it is then silently discarded). Key on ticker plus start date, prune old
    entries, and write to a temp file then rename.
20. **Form validation gaps:** `buy_date` is stored as free text (not parsed), a sell
    date before the buy date is accepted, and a missing ticker raises a raw
    `KeyError` message.
21. **Python environment depends on another tool's runtime.** `.venv` was built
    from Python at `~\.cache\codex-runtimes\...`. If that folder changes, the app and
    scheduler stop starting at login. Rebuild `.venv` from a normal Python 3.12.

## P3: structural

22. **No migration versioning.** `db.py`, `options_db.py` and `fund_management.py`
    each run `CREATE`/`ALTER TABLE` on every import. This already caused a
    first-start race in Docker. A numbered migrations table would make upgrades
    predictable.
23. **Duplicated calculations that can drift apart:** `realized_pl` exists in both
    `app.py` and `scheduler.py`; option max-risk is written twice
    (`options_db.calculated_max_risk` and `option_charges.calculated_option_max_risk`).
    Keep one copy in `services/`.
24. **Very large modules:** `app.py` is 3,330 lines (41 routes),
    `v1_report_generator.py` 2,644, `scheduler.py` 1,440, with report HTML
    built inside Python strings. Split by area (stocks, options, funds, reports)
    using Flask blueprints, as `fund_management.py` already does.
25. **No tests for the web layer.** The 50 tests cover calculations and the
    scheduler. None cover login, permissions, CSRF or user isolation, which is
    where items 3, 12, 13 and 15 live.
26. **Noisy logs:** every request writes two log lines (INFO plus DEBUG with form
    keys) to the daily log file.
27. **NSE holidays are a hand-edited list** in `config.ini`; 2027 will need updating.
28. **`/health` is public and shows the server's file path** for the heartbeat file.
    Minor, but drop the path from the public response.

## What looked solid
- Every page except `/health`, `/login`, `/logout` and the key-protected API requires
  login, and the funds blueprint has its own guard.
- CSRF is checked on every POST.
- Bet, group and alert edits and deletes look the record up through the owner-filtered
  query first. (Option strategy delete did not; found and fixed in the P3 round.)
- Option P&L is recalculated from the legs on every edit, not left stale.
- The scheduler's single-instance lock, heartbeat and stale-heartbeat alert work.

## Suggested order
1. Alert de-duplication (item 1): the biggest daily improvement.
2. Automated, correct backups (item 2): the biggest risk.
3. Bootstrap password and open redirect (items 3, 12): small, contained fixes.
4. Decide on the public report contents (item 4).
5. Fund pricing and cash-flow dates (items 5–7) before adding more investors.
6. Net-of-charges P&L (item 17).
